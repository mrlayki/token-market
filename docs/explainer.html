05LiteLLM 负责什么

LiteLLM 有两种用法：作为独立网关（LiteLLM Proxy，自带 Key、模型、预算数据库），或者作为 Python 库（SDK）。本项目只把它当 协议转换库 用，而且只在跨协议时才调用。

为什么不用 LiteLLM Proxy：它自己维护一套 Key 表和模型表，渠道和令牌会在两边各存一份、需要同步；它的预算按美元累计，表达不了「套餐包 + 钱包」的多桶 Token 额度；渠道优先级、多 Key 轮询、自动禁用这些也要迁就它的路由模型。所以网关自研，LiteLLM 只做最难写对的那部分。

09预扣费怎么算

预扣的目的是：在调用上游之前，把这次请求最多可能花的钱先冻结，确保冻结成功的请求一定付得起。上游返回后再按实际用量结算，多冻结的退回。

预估用量

  • 输入 token：用 tiktoken 对请求本身计数。每条消息加 4 个结构 token，图片按 1,000、文档按 2,000 估，tools 定义按 JSON 文本计。输入在请求发出前就确定，估得比较准。
  • 输出 token：输出长度事先未知，所以取请求里的上限：max_completion_tokens / max_tokens / max_output_tokens；没传时用配置 billing.default_max_tokens（默认 4,096）。再和两个上限取较小值：配置 billing.max_est_output_tokens（默认 32,768）、模型的最大输出。
  • embeddings：只有输入。

所以答案是：基于 max_tokens，并加了上限。max_tokens 是上游会生成的硬上限，按它冻结，正常情况下结算时只会退款、不会补扣。

分桶冻结（reserve.lua）

  1. 选出适用当前模型、未过期的套餐包，按到期时间升序。
  2. 每个包按自己的计量规则算所需 token：输入 × 输入权重 + 输出 × 输出权重。包够用就全部由它覆盖；不够就覆盖一部分，记下剩余比例 f。
  3. 剩余比例换算成钱包金额：f × 预估售价，检查钱包可用余额和令牌额度上限。
  4. 全部检查通过后才写入：套餐余量减少、钱包可用 → 冻结、令牌额度减少，并保存预扣单（分配明细 + 结算上下文 + TTL）。任一项不足直接返回 402，什么都不改。

计算示例

claude-sonnet-5-5，售价输入 ¥14.4 / 输出 ¥72 每百万 token，default 分组（倍率 1）。请求输入 1,200 token，max_tokens=2000，实际输出 350 token。

预估售价
1,200 × 14.4 + 2,000 × 72 = 161,280 微元（¥0.161280），冻结
实际售价
1,200 × 14.4 + 350 × 72 = 42,480 微元（¥0.042480），扣除
退回
118,800 微元

套餐包示例：「DeepSeek 千万包」输出按 4 倍计量，同样的预估用量需要 1,200 + 2,000 × 4 = 9,200 token。如果包里只剩 5,000，它覆盖 5,000 / 9,200 ≈ 54.3%，剩下 45.7% 按售价走钱包。结算时按同样顺序和实际用量重新分摊。

结算（settle.lua）

  • 按预扣时的分配顺序，用实际用量重新计算每个桶该扣多少；没用完的冻结退回。
  • 实际超过冻结（预估偏差，例如上游不认 max_tokens）时，从可用余额追加；允许透支到 billing.overdraft_limit（默认 ¥0.5），再超出的记为 shortfall 并告警。
  • 同一个脚本里 XADD 计量事件，额度变化和待落库事件不会只发生一半。
  • 预扣单被删除后再结算会返回「无预扣单」，重复结算天然幂等。
取舍：max_tokens 很大时（例如 128K 输出的模型），按上限冻结会让余额较少的用户被提前拒绝，即使他实际只用一点点。目前用 32,768 的估算上限缓解，代价是极端长输出要靠透支额度兜底。更精细的做法是「流式过程中按实际输出增量追加冻结，追加失败就截断」，这一项尚未实现。

10并发防超卖

「先查余额，调用完再扣」在并发下的问题：N 个请求同时查到同一个余额，全部放行。Redis 单线程执行 Lua 脚本，脚本内部的「检查 + 冻结」不会被其他请求插入，所以不会超卖；冻结后的余额对后续请求立即可见。

实测：余额 ¥1.00，300 个并发请求各需 ¥0.01，理论上最多成功 100 笔。

先查后扣
超卖 200 笔
300 个请求全部成功，余额 −¥2.00
Lua 原子预扣
超卖 0 笔
成功 100 个，余额 ¥0.00

端到端（Docker 全栈，经 Nginx）：余额 ¥0.002，500 个并发流式请求，成功 15、额度不足拒绝 485、其他错误 0；余额未为负，Redis = PostgreSQL = 流水合计，三项对账一致。

余额购买套餐、管理员扣款这类非调用的扣减，同样先在 Redis 冻结金额，再写 PostgreSQL，避免和正在进行的调用争抢同一笔余额。

11热数据与账本一致

Redis 里的余额是「热副本」，PostgreSQL 的流水是「账本」。两者的关系：

场景做法
首次访问Redis 没有该用户时从 PG 快照加载（load.lua 只在不存在时写，并发加载只生效一次）
调用扣费Redis 先扣，计量事件经 Stream 由 worker 写入 PG（扣余额 + 写流水在同一事务）
充值、兑换、调整、发套餐、过期PG 事务内写余额、流水、ext_version + 1、outbox；提交后立即投递到 Redis，失败由 worker 每 5 秒重试
加载和充值同时发生apply_ext.lua 只应用版本号大于「加载时版本」的变更，并按操作 ID 去重，避免重复入账
进程崩溃留下的预扣预扣单 TTL 是回收期限的 2 倍；worker 扫描到期预扣，按预估值保守结算并标记 reaped
Redis 宕机降级为 UPDATE wallet … WHERE balance >= :x 条件扣减（同样原子），变更写 outbox，恢复后同步回 Redis；也可配置为直接拒绝
持续核对Redis（可用 + 冻结）= PG 余额，仅在计量流无积压、无待同步 outbox 时比对；有差异可一键重建

OpenAI 兼容请求时注入 stream_options.include_usage=true，末尾多一个只含 usage 的包；客户端本身没要求的话把这个包吞掉，对客户端透明。缓存命中取 prompt_tokens_details.cached_tokens，DeepSeek 取 prompt_cache_hit_tokens

  • 断开也一定结算：客户端断开时生成器被取消，finally 里用 anyio.CancelScope(shield=True) 屏蔽取消，保证「关闭上游连接 + 结算」执行完。关闭上游很重要：否则上游继续生成，平台照样付钱。

  • 三层保障：流结束时结算 → 结算没执行到时由预扣回收任务兜底 → 落库失败由消费者组重领，10 次失败进死信并通知管理员。

13渠道路由与健康

一个模型能被调用需要三样：模型（对外名称、上架）、价格、渠道（真正提供它的上游）。渠道保存时，把「分组 × 模型」展开写入 ability 表；relay 把它常驻内存，控制面修改后通过 Redis 版本号在 1 秒内生效。

  1. 按请求的模型和用户分组取出候选渠道，按优先级从高到低分档。
  2. 第 N 次尝试用第 N 档，档内按「权重 + 10」加权随机（避免权重为 0 的渠道永远选不到）。
  3. 渠道内多 Key 随机或轮询（轮询用 Redis INCR），跳过冷却中的 Key。
  4. 渠道的模型映射把对外名称改写成上游真实模型名，响应里再改回对外名称。

健康管理：401 / 403 或错误信息命中「欠费、Key 无效」等关键词时禁用该 Key，渠道所有 Key 都不可用就禁用渠道并通知；429 / 5xx 冷却该 Key 30 秒；单个、批量、定时测试成功后自动恢复「自动禁用」的渠道（手动禁用的不动）。

14计费、账单与对账

项目设计
售价公式⌈(普通输入 × 输入价 + 缓存读 × 缓存读价 + 缓存写 × 缓存写价 + 输出 × 输出价) / 10⁶⌉ × 分组倍率，向上取整到微元；按次计费模型取固定价
价格版本改价是新增一个版本，可设未来生效时间；已生效版本不可删除，历史账单可追溯
分时计价价格版本可配置时段规则（星期、起止时间、时区、倍率），按请求开始时刻命中第一条并写入价格快照，同一请求不跨时段变价。DeepSeek 默认按低谷价为基础价，工作日 09:00–12:00、14:00–18:00 ×2。渠道成本默认跟随售价时段，也可单独配置采购时段（对用户统一价、上游分时计费时使用）
按量预充值钱包，充值金额 × 分组充值倍率 × 满额折扣
套餐包售价、token 数、适用模型或供应商、有效期、每人限购、输入 / 输出计量权重；售出后快照规则，商品后续修改不影响已售
成本与毛利渠道成本倍率 × 原价 = 每笔成本，看板显示营收、成本、毛利
订单下单 → 收银台 → 网关 HMAC 签名回调 → 验签与金额比对 → 行锁幂等发货；已收款发货失败停在 paid，可补发货
账单日账单次日生成、月账单次月生成，生成后不可变：期初、期末、充值、消费、退款、套餐抵扣、分模型明细
平台内对账① 钱包余额 = 钱包流水之和，套餐剩余 = 套餐流水之和 ② 每笔调用的扣费 = 对应的消费流水 ③ Redis 热数据 = PG 余额。每小时自动执行，管理端可手动执行、查看差异、标记处理
与厂商对账（账单）按渠道导入厂商用量账单 CSV（兼容常见中英文列名、美元按汇率折算，同一天同一模型重复导入会覆盖），与平台按「对账时区的日期 × 上游模型」聚合的请求数、输入 / 输出 token、渠道成本逐行比对，超过容差（默认 1%）标记差异，并识别「仅平台有 / 仅上游有」
与厂商对账（余额）对有余额接口的厂商（DeepSeek），worker 每小时记录余额快照；任选两次快照，余额减少量 = 上游实际扣费，与平台在同一时间窗内对该渠道核算的成本比对；余额上升会提示期间可能有充值
